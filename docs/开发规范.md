# 开发规范

本页规定「怎么改工作流」。结构总则见 `PROJECT_STRUCTURE.md`，Agent 入口见 `AGENTS.md`。

## 版本隔离

- 不直接覆盖 `workflows/baseline/`
- 不直接覆盖 `workflows/release/`
- 实验必须创建新版本文件
- 除明显错误外，不覆盖历史实验 JSON 和 `EXP-*.md`

生命周期：

```text
Baseline → Experiment → 测试 → 调整 → 确认稳定 → Release
```

任何实验都从明确的基线或已有实验派生，并在实验文档里写清来源。

## 修改前先分析

大规模调整前先回答：

1. 当前数据流是什么？
2. 每个关键节点负责什么？
3. 当前问题可能来自哪一段？
4. 哪些节点与问题无关？
5. 最小修改方案是什么？
6. 是否会超过约 6 GB VRAM？

禁止在没看懂工作流结构时随机大改。

## 单变量实验

调试人物一致性时，禁止无目的地同时改大量参数。

例如测 IPAdapter 权重：

```text
Experiment A    weight = 0.70
Experiment B    weight = 0.75
Experiment C    weight = 0.80
```

其他条件原则上保持一致。一次改多个变量时，结论里不得声称「某一个参数有效」。

## 设计约束

- 优先解决 `docs/已知问题.md` 里已编号的明确问题
- 避免无意义增加节点
- 避免重复模型加载
- 必须考虑 VRAM
- 不得随意更换基础模型；换模型本身就是一次独立实验
- 不得为了一个指标明显破坏更高优先级指标（见 `docs/项目目标.md`）
- 不得使用无法确认存在的节点或模型而不加说明
- 参考图放 `references/`，生成图放 `results/`，不要混

## 命名

```text
功能-方案-v版本.json
```

示例：`character-base-v01.json`、`character-ipadapter-v02.json`。

正式版：`character-consistency-v1.0.json`。

禁止：`最终版.json`、`最新.json`、`111.json`、`test123.json`。

## 实验记录

每次重要实验新建 `experiments/YYYY-MM-DD/EXP-XXX.md`，字段以 `experiments/EXP-TEMPLATE.md` 为准。

完成后：

1. 工作流放入 `workflows/experiments/`
2. 结果放入 `results/experiments/` 或 `results/comparison/`
3. 追加 `logs/experiment-log/INDEX.md`
4. 项目级变化追加 `logs/CHANGELOG.md`
5. 有效参数写回 `docs/参数说明.md`
6. 新问题写回 `docs/已知问题.md`

## 晋升规则

- **进入 Baseline**：能稳定跑通，并作为后续对比对象。写入后原则上不再改文件本身。
- **进入 Release**：核心目标通过实测，且本机可稳定运行。未测试不得标记为正式版。
- **进入 Archive**：方案淘汰或架构过时，但保留调试价值。失败实验不要直接删。

## 交付格式

重要修改至少汇报：修改了什么、为什么改、新文件路径、与 Baseline 的差异、结论、下一步。
